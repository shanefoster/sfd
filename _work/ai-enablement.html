The Problem

When we started testing an AI-assisted design-to-engineering workflow (using Figma’s MCP Dev Server), one thing became immediately clear: the agent is only as good as the context we give it.

Our core design system components translated well, because they’re built with consistent tokens, structure, and naming.

The moment we pulled in shared, product-specific components, things started to drift and engineers had to step in to interpret intent again.

  • arrow_right_alt Building screens in RN required interpretation, back-and-forth, and manual assembly.
  • arrow_right_alt Agents can move fast, but only when the design artifacts are semantically consistent.
  • arrow_right_alt Core DS components performed well; shared components caused accuracy + consistency issues.

So the real problem wasn’t “can the agent build screens?” It was “can we make our design artifacts reliable enough that the agent can’t misinterpret them?”

Automation

Automating the workflow with Figma's agent and Skills

Preparing components by hand didn't scale across every product team. I encoded our standards into a set of native Figma Skills, published to the whole org, so Figma's agent can do the prep work and designers only review and answer questions.

The Skills run as a four-step pipeline: annotate → describe → audit → document. Each step builds on the output of the step before it. Reads happen automatically, and any write to a component needs explicit confirmation.

Step 1

annotate-component

  • arrow_right_alt Writes native Dev Mode annotations as first-pass drafts, using the correct category for each.
  • arrow_right_alt Writes the questions a designer has to answer, and marks each one [DRAFT] until a human edits it.
  • arrow_right_alt Triages a library to find which components are worth annotating, and never deletes an annotation.

Output from annotate-component on a Callout component. The questions still marked [DRAFT] are waiting for a designer to answer them.

Step 2

describe-component

  • arrow_right_alt Builds the component's description field from the annotations written in Step 1.
  • arrow_right_alt Pulls in six sections from annotations (Interaction, Behavior, Motion, Accessibility, Content, Platform) and flags any that are missing.
  • arrow_right_alt Checks the authored sections with the designer before writing them, and shows unreviewed drafts as gaps, not as content.
Step 3

handoff-audit

  • arrow_right_alt Checks every applied variable against the approved Semantic Variables library and nothing outside it.
  • arrow_right_alt Checks for semantic layer names, full annotation coverage, a clean description field, and Code Connect.
  • arrow_right_alt Places a scorecard frame on the canvas that summarizes whether the component is ready for engineering.
Step 4

document-component

  • arrow_right_alt Writes a markdown doc for the component that's ready to publish to Zeroheight.
  • arrow_right_alt Builds a visual doc frame on the canvas with variants, do/don't examples, and states.
  • arrow_right_alt Creates a separate anatomy frame, ready to annotate.
