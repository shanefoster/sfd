Identifying the Problem

We were headed toward a predictable failure mode

As teams shipped more features, more patterns popped up that felt reusable.

Most the team was unfamiliar with how to work with a mature, centralized design system.

The default mindset became:

"If anyone might use it again, it belongs in the core design system."

Which leads to:

inventory_2

Core bloat

Product-specific edge cases and near-duplicates started creeping into the core library.

block

No official alternative

Teams needed to share work, but if core was the only "blessed" path, everything got funneled into it.

psychology_alt

Hard to grasp

"Not everything belongs in core" sounds simple, but teams struggled to apply it — especially when confident their component was "reusable."

Goal: Keep core clean and enable reuse across teams through modular shared libraries.

The Solution

A Tiered Library Model

Instead of "core or nothing," we introduced a tiered system:

Tier 1

Core Design System

Foundational, cross-product patterns with a high bar for stability and long-term governance. Managed by the system team.

Tier 2

Shared Product Libraries

Reusable product-level components owned by feature teams. Shared across teams when helpful, without forcing system-level maintenance.

Tier 3

Local Libraries

Niche patterns specific to one product area. No need to pretend they're universal.

The difference between "system foundation" and "reusable product pattern" is... scope.

Education

Making it click

The win wasn't just creating tiers — it was making the model usable. We shifted the default question from:

cancel

"Is this good enough for core?"

check_circle

"What tier does this actually belong to?"

That subtle change reduced friction immediately, because "not core" didn't mean "no." It meant:

  • arrow_right_alt Shared, if it's reusable across multiple teams/products
  • arrow_right_alt Local, if it's specific and not worth centralizing

Implementation

Making it work in Figma: Structure + Naming

Governance only works if the day-to-day experience supports it.

We created two new projects that contained libraries for shared product components and patterns.

Visibility into ownership makes the whole model work.

Library structure (discoverability)

We created a predictable file/page model so teams could find shared patterns instead of rebuilding them.

{% include insight-callout.html label="Why structure mattered" icon="folder" text="We had multiple games that shared core components that slightly changed based on regulations, so having them sit side-by-side for context was extremely important." %}

Predictable structure prevents "I didn't know that already existed."

Naming (semantic clarity)

We reinforced naming patterns that encode intent and scope — so "Card" doesn't become 37 different things.

Same base pattern, scoped by product context, still reusable.

Process

Governance without bureaucracy

Shared libraries only help if people trust them. So we kept governance lightweight, but clear.

Roles + ownership (no orphaned libraries)

We defined who owns what, who triages, who maintains, and how shared work gets promoted.

Ownership is the difference between "shared system" and "random file someone made."
